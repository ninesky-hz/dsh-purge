# 1.7.18 — 对齐 DSH Desktop 0.2.2-rc.3

上游这一版没有动工具面，也没有动任何被补丁改写的文件。它修的是**安装器**里一个 Windows 场景：应用内更新下载完、准备 rename 安装目录时，后台那个「正在重启」的状态窗口（`rundll32.exe` 起的一个 StatusWindow）继承了安装目录作为工作目录，把目录锁住，rename 失败，更新完成也打不开。

修法只有一行：`restart-status.h` 里给 `CreateProcessW` 传 `launch->directory`（System32），不再传 `nullptr`。另外新增了一个实验性 `deepseek-chat-import` 包。

所以本版的工作是**复核**而不是适配：把 rc.3 拿全、逐字节比对、在副本上真打两遍，确认 82 条锚点一条没漂。补丁表一条未改。

## 复现步骤

```sh
# 1) npm 包基线（45 个包各自 version=0.2.2-rc.3）
node .work/rc3/extract-packages.mjs     # → .work/rc3/host/node_modules/@deepseek-ai

# 2) 逐条诊断（输出 drifted / optionalDrift / partialDrift / missing）
node .work/rc3/run-drift.mjs            # → .work/rc3/drift.json

# 3) 副本上真打两遍（独立 DSH_HOME，不碰真实 profile）
node .work/rc3/apply.mjs desktop        # → .work/rc3/apply-report-desktop.json
```

`run-drift.mjs` / `apply.mjs` 的 `aiBase` 必须指到 `.../node_modules/@deepseek-ai` 这一层；传上层会得到 0 个目标键、全部误判 `missing_file`。

## 验收：`npm test` 读数与两处夹具修复

本机全量：**462 条 / pass 437 / fail 3 / skip 22**。

剩下 3 条全部在 pristine HEAD（`ab6c3e5`）上用 `git worktree add --detach` 起一份干净工作树复跑，**同样失败**，与本版改动无关：

- `update-download.test.mjs` 两条 —— 断言仍写死 GitHub 默认源（`https://api.github.com/repos/...`），而本仓库的默认发行源已是 Gitee（`lib/update-source.js:14-15` 的 `DEFAULT_REPOSITORY = "n-sky/dsh-purge"`、`DEFAULT_PROVIDER = "gitee"`），另一条还依赖真实发行源 API 的返回形态。
- `update-proxy-runtime.test.mjs` 的真实 CONNECT 隧道用例（1.7.9 起就在基线里）。

顺手修掉的两处问题都在 `test/community.test.mjs` 里，**生产代码一行未改**：

1. **夹具打包用了 PATH 里的 tar。** Windows 上 PATH 的 tar 若是 Git-Bash 的 GNU tar 1.35，会把 `-C C:\...` 和归档路径里的 `C:` 当成远端主机，直接报 `tar: Cannot connect to C: resolve failed` —— 34 条用例里有 27 条在 `setup()` 就崩，rc.3 那条白名单用例根本跑不到。现在测试与生产代码（`lib/community.js:960-961` 的 `validateArchive`、`lib/rollback-transaction.js`）用同一套选择：Windows 走 `System32\tar.exe`，其余走 `tar`；三处调用点（一处 `-czf`、两处 `-xOzf`）统一到 `TAR()`。改完 34 条都能跑：**33 pass / 1 skip**（POSIX 启动器用例在 Windows 上跳过），耗时从 140 s 降到 4 s。
2. **夹具的 `repository.url` 写死了旧仓库地址。** `validateArchive()` 的身份校验只接受「本清单声明的仓库 + 当前发行源能产出的地址」（`acceptedRepositoryUrls()`）；默认源切到 Gitee 之后，6 条用到候选包的用例全部误报 `安装包身份与发行版本不一致`。现在夹具跟随本清单自己的 `repository.url`（`fixtureRepositoryUrl()`），换 checkout、换源都不会误报。

## 附带：自检读取性能，以及它引入的一处致命回归

面板在 rc.3 这台机器上报「未定位到宿主 / 读取失败: timeout」。根因不是权限，是**同一批宿主文件被反复读**：82 条补丁逐条读 `main.js`、各 `lib/index.js`（单个几 MB），`core` 侧 selfcheck 要 13 s（CLI）/ 40 s+（宿主内建 HTTP，面板 10 s 就超时）；`desktop-identity` 侧一次 `targetFiles` 会让 `archiveReader` 跑 327 遍，每遍重读几 MB 的 ASAR 头部，实测读掉约 1.7 GB / 11 s。

两处缓存一并进本版，键都是 `mtimeMs + size`，宿主文件被改写后自然失效：

| 位置 | 改动 |
| --- | --- |
| `lib/core.js` `loadText()` | 文本缓存（上限 96 条）；`saveText()` 写盘后主动 `delete` 键，避免 mtime/size 撞车回旧值 |
| `lib/desktop-identity.js` | `readArchiveHeader()` 复用头部解析结果（上限 8 条）；`archiveReader()` 只负责按头部取条目 |

**评审时发现并修掉的回归（本版必须带着一起发）**：`loadText()` 用 `await fsp.stat(p)` 判失效，而 `fsp = hostFs.promises`——`hostFs.promises` 当时只有 `readFile / writeFile / mkdir / unlink / rm / copyFile / rename`，**没有 `stat`**。于是 `fsp.stat is not a function` 被 `patchDrift` 的 `catch` 吞成 `reason: "read_error"`，表现是**每一条补丁的每一个目标文件都读不到**：

| | 修前 | 修后 |
| --- | --- | --- |
| `checked` | 82 | 82 |
| `applied` | **10** | **82** |
| `drifted` | 全部（read_error） | `[]` |

Electron 里是同一个 `hostFs`，所以这不是「只在 CLI 上」的问题——装上本版点「应用」会变成 82 条全部读不到、一条也打不上。

修法（`lib/extract-asar.js:172-175`）：

```js
// stat 必须跟着 readFile 一起按归档影子选 fs：core 的文本缓存用 mtime/size 判失效，
// 少了它 fsp.stat 就是 undefined，每条补丁都读失败（表现为全体 read_error/漂移）。
stat: (p, ...args) => fsFor(p).promises.stat(p, ...args),
```

回归测试：`test/host-backup.test.mjs` 新增 `hostFs.promises exposes every method core uses (stat included)`——断言 `stat/readFile/writeFile/mkdir/unlink/copyFile/rename` 全在，并实际 `stat` 一次（`size` 与 `mtimeMs` 类型）与一次 `ENOENT`。

实测：`drift-rc2` 对真实 rc.3 宿主 `applied 82 / drifted 0 / optionalDrift 0`，单次 1.5 s。

## 升级提示

- 本版只加了一条宿主版本白名单（`0.2.2-rc.3`），**补丁内容一条未改**。已经装过 1.7.17 的机器，升级后照样要手动「应用」一次再完整退出重开——补丁写盘不等于当前进程加载。
- DSH 更新到 rc.3 之后，安装器那个修复才会生效；它与本插件的 #45 / #46（桌面壳的更新交接）是两件事：前者修 rename 被锁，后者防 shell 在交接时挂死。两条都留着。
- rc.3 新增的 `dsh-deepseek-chat-import` 是实验性插件，是否启用由你自己的 profile 决定；本插件不为它写任何补丁，也不进预设行。
