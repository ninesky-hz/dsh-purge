# 1.7.15 — 运行副本版本诊断

把插件副本从 1.7.13 手工覆盖成 1.7.14 之后，运行中的 DSH 仍然执行旧代码：面板里没有「删除备份」按钮，也没有任何提示说它为什么不在。这个版本补上的不是功能，而是**一句真话**：磁盘上装着哪一版、当前进程里跑的是哪一版，两者不一样的时候，明确告诉你必须完整退出重开。

## 事故链：三件事被当成了同一件

1. **换副本**：把新版本的目录覆盖到 profile 的安装副本上。这一步只改磁盘。
2. **加载代码**：进程启动时才发现并执行新的插件模块。这一步只发生在「打开 DSH」的那一刻。
3. **刷新界面**：`Cmd/Ctrl+R` 重新拉前端 bundle。这一步只换浏览器里的 JS/CSS。

第 1 步做完、第 2 步没发生，就会出现「文件是新写的、行为还是旧的」。而第 3 步容易被误当成第 2 步：刷新浏览器确实会换掉界面代码，但后端路由、插件运行时模块、宿主补丁全在 Electron 进程里，刷新一万次也不会重新加载。

更麻烦的是**旧代码无法自报旧**。想要一条「你是旧代码」的提示，就得有人在新版本里写这个判断；旧进程跑的是旧模块，那段判断根本不存在于它的内存里。所以事故当时面板一片安静是必然的，不是这次改动没生效——那时它还没被加载。

## 两个事实：磁盘与内存

`lib/update.js` 里本来就是两个函数，只是以前没有任何接口把它们的差异暴露出来：

| 事实 | 来源 | 语义 |
| --- | --- | --- |
| `disk_version` | `localVersion()`：每次调用都读 `PLUGIN_ROOT/package.json` | 磁盘上现在装着哪一版；换副本后立刻变化 |
| `running_version` | `runningVersion()`：返回模块求值时捕获一次的 `LOADED_VERSION` | 这份进程实际在执行哪一版；只有重启才会变化 |
| `plugin_version` | 与 `running_version` 同源 | 既有字段，语义不变，面板徽标用它 |
| `panel_version` | `panelBundleVersion()`：读包内 `client.js` 头部 `// panel-version:` | 界面 bundle 是哪次构建的（1.7.10 起） |

新增字段只有前两个。`/dsh-purge/status` 与 `/dsh-purge/community` 的 GET 各带一份：

```json
{
  "plugin_version": "1.7.14",
  "running_version": "1.7.14",
  "disk_version": "1.7.15",
  "panel_version": "1.7.14"
}
```

`plugin_version` 保持原样，`version`（community 接口）也保持原样；`disk_version` / `running_version` 是纯增量。

## 面板提示

`CommunityMaintenance` 在「维护 → 本机备份」小节标题之前插入一条通知，只在 `disk_version` 与 `plugin_version` 都存在且不相等时渲染：

> 磁盘上已是 1.7.15，当前进程还在运行 1.7.14：完整退出 DSH（从系统托盘退出）再打开才会加载新代码，刷新浏览器不够。

- 两个版本号都取自后端响应（`value.disk_version` / `value.plugin_version`），没有任何写死的字符串。
- 任一字段缺失或两者相等 → 不渲染。缺失时不猜，避免在旧后端（还没有这两个字段）上误报。
- 用的是既有的 `dshpp-notice`（`role="status"`）。理由：这是一条**需要用户马上行动**的告警，和本节底部的操作结果通知同一语义；`dshpp-hint` 是页脚那种次要说明（「备份只保存在本机……」），读起来像附注，压不住「你现在看到的是旧界面」这件事。

## 排查步骤

1. 打开 `/dsh-purge/status`（面板会自己请求），看 `disk_version` 与 `running_version`：
   - **相等** → 磁盘与进程同源，问题不在这里。
   - **disk 比 running 新** → 新副本没被加载。**完整退出** DSH（系统托盘 → 退出，不是关窗口），再打开一次。
2. 重开后仍不相等，说明运行时读的不是你以为的那份副本。插件运行时读的是 profile 下的安装副本：
   `$DSH_HOME/profiles/<profile>/node_modules/dsh-purge-community/package.json`
   它的 `version` 才是 `disk_version` 的来源；工作目录里改代码不影响运行时。
3. 这一份被换成了另一版（例如回滚过、或装了另一条依赖 spec）时，把目标版本重新装到该 profile，再完整退出重开。
4. `panel_version` 与 `plugin_version` 不相等是另一回事（界面 bundle 不是当前版本构建的），走 1.7.10 的说明重建 `client.js`，与本节的「进程没加载」分开判断。

## 校验

- `packages/purge-panel`：`npm test` 全绿；新增两条 —— 不一致时出现「完整退出」提示且同时含 `1.7.15` 与 `1.7.14`，一致/缺失时不出现。
- 根：`test/plugin-lifecycle.test.mjs` 在真实 `/dsh-purge/status` handler 的响应上断言 `plugin_version` / `running_version` / `disk_version` 三个键，并断言本进程 `localVersion() === runningVersion() === package.json` 的 `version`（同源一次捕获）。
- 两份 `client.js` 已按 1.7.15 重建：`npm run check:client` 字节一致；`npm run check:docs` 输出 1.7.15。
- 没有新增宿主补丁、没有改锚点；升级后照旧只需手动「应用」+ 完整退出重开一次。

## 一句总结

这个版本不会阻止你「覆盖副本后继续用旧代码」，但至少会让面板告诉你正在发生这件事——前提是先把新版加载起来一次，因为在旧代码里没有这段判断。
