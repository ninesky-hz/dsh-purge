# 1.7.19 — 「应用」不再被 runtime 修复挡死

密封桌面（`app.asar` 还在）点「应用」，补丁写进 `resources/app/` 之后，请求在最后一步返回 500：

```
失败: Desktop CLI runtime repair failed; original archive retained.
```

日志里 `cli_repair` 是 `{ok:false, reason:"missing_runtime"}`。补丁其实已经全部落盘，只是这句话把整个响应判成失败，面板上看不到任何东西，用户会以为「应用」根本没生效。

## 谁报的

`lib/index.js` 的 apply handler（当时 2321–2335 行）：

```js
cliRepair = core.repairOfficialCliAfterUnpack();
const sealedNow = core.desktopAsarStillSealed();
if (handoff && sealedNow && cliRepair?.ok === false) {
  sendJson(response, 500, { ok:false, error: "Desktop CLI runtime repair failed; original archive retained.", cli_repair: cliRepair });
}
```

判据是 `ok === false`，不区分「写盘失败」和「依赖还没就位」。

## 为什么会 `missing_runtime`

`repairOfficialCliAfterUnpack()` → `desktop.js` 的 `ensureAppRuntimeLink(resources)`，最后落到 `lib/runtime-layout.js`：

```js
const PNPM_ENTRY = "primary-runtime/dependencies/pnpm/bin/pnpm.mjs";
if (!fs.existsSync(app) || !pnpmEntry || ...) return { ok:false, reason:"missing_runtime", ... };
```

`resources/runtime` 里必须有 `primary-runtime/dependencies/pnpm/bin/pnpm.mjs`。而这个目录**不是安装包自带的**：DSH 启动时才会把用户级运行时接进来，形成一个 junction 树：

| 链接 | 指向 |
| --- | --- |
| `resources/runtime/primary-runtime` | `$DSH_HOME/dsh-runtimes/dsh-primary-runtime` |
| `resources/runtime/bin` | `…/dsh-primary-runtime/dependencies/node/bin` |
| `app/runtime` | `resources/runtime` |

宿主启动流程跑完之前，`resources/runtime` 可能是个空目录（本机实测 `count = 0`）。用户在这个窗口里点「应用」，就必然拿到 `missing_runtime` —— 而它跟补丁写没写进去毫无关系。

本机复现顺序：第一次调用返回 `missing_runtime`；几分钟后再调用同一个函数，junction 已由宿主建好，返回 `ok:true`。

## 修法

`lib/core.js` 新增一个判定函数，放在 `repairOfficialCliAfterUnpack()` 之后：

```js
const CLI_REPAIR_ENV_MISSING = new Set(["missing_runtime", "not_official", "no_resources"]);

export function cliRepairBlocksApply(cliRepair) {
  if (!cliRepair || cliRepair.ok !== false) return false;
  const reason = String(cliRepair.reason || cliRepair.symlink?.reason || "");
  return !CLI_REPAIR_ENV_MISSING.has(reason);
}
```

- `missing_runtime` / `not_official` / `no_resources`：环境还没就位，不拦。补丁已经写盘，换包继续，宿主下次启动自己会把 runtime 接上。
- `link_repair_failed` / `rollback_failed` / `runtime_conflict` / `backup_failed`：真写盘问题，仍然 500。
- 没有 `reason` 的异常：保持原行为，仍然 500。

handler 改成 `core.cliRepairBlocksApply(cliRepair)`。

**一处容易漏的细节**：`reason` 不在顶层。`desktop.js` 把 `ensureAppRuntimeLink()` 的返回值整个挂到 `report.symlink` 上：

```js
report.symlink = ensureAppRuntimeLink(resources);
```

所以顶层 `cliRepair.reason` 是 `undefined`，真值在 `cliRepair.symlink.reason`。第一版只看顶层，复测时 `blocks apply` 仍为 `true`；改成两级都看之后才变成 `false`。

## 回归

`test/runtime-layout.test.mjs` 新增：

```js
test("apply is not blocked when the official runtime is simply absent", () => { ... });
```

断言 8 种输入：`null`、`{ok:true}`、三个环境类 reason → `false`；四个写盘类 reason、以及 `{ok:false}` 没有 reason → `true`。

```
node --test test/runtime-layout.test.mjs   # 18/18
```

## 升级

改的是插件运行时模块（`lib/core.js`、`lib/index.js`），覆盖 profile 的 `node_modules/dsh-purge-community` 之后要完整退出重开 DSH 才加载。磁盘状态不代表当前进程已加载。
